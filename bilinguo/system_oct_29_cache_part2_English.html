Section 1 — Comparing the 4 patterns (Pattern comparison)

Read this first: this section is a comparison summary of Section 4 already learned in Session 7 — it is not brand-new content. Session 7 introduced each cache access pattern; this section puts all four side by side and compares their read / write flows and pros / cons.

Link back to Session 7 — Section 4: the 4 cache access patterns. That section's main content: how the application reads and writes data through the cache — cache-aside, write-through, write-behind, refresh-ahead. This section does not teach them again from scratch; it only compares them with each other.

Example 1.1 — Cache-aside (lazy loading)

READ

The application checks the cache first. On a hit, it returns the data right away. On a miss, it reads the database, fills (populates) the cache, and then returns the data.

WRITE

The application writes directly to the database, then invalidates or updates the matching entry in the cache.

Pros
  • Simple and easy to implement.
  • Only data that is actually read gets cached — no memory is wasted on data nobody uses.
Cons
  • Every miss costs 3 trips: cache → DB → cache.
  • The data in the cache can go stale.
  • A new cache node starts empty.

Example 1.2 — Write-through

WRITE

On every write, the application writes to the cache and the database together (synchronously), and only then returns.

READ

Reads come from the cache as usual. Because every write goes through the cache, the data in the cache always matches the database.

Pros
  • The cache is always fresh — the cached data always matches the database.
Cons
  • Writes are slower, because both stores must be written before returning.
  • Data that nobody reads is cached too — wasted memory.
  • A new node stays empty until the first update is written through it.

Example 1.3 — Write-behind / Write-back

WRITE

The application writes to the cache and returns immediately. The database is written asynchronously later, by the cache itself.

READ

Reads come from the cache — and because writes also land in the cache first, a read right after a write sees the newest data in the cache.

Pros
  • Very fast writes — the user never waits for the database.
Cons
  • Data loss if the cache crashes before it writes to the database.
  • Complex to implement.

Example 1.4 — Refresh-ahead

READ

The cache refreshes entries that were recently read, just before they expire. The next reader gets the fresh copy from the cache right away.

WRITE

The write flow is unchanged — what makes this pattern different is the read side: reloading the data happens ahead of time, instead of waiting for a reader to miss.

Pros
  • Lower read latency — fewer readers suffer a miss and have to wait for the database.
Cons
  • If the prediction is wrong — refreshing data that nobody reads again — it is worse than doing nothing: the work and the resources are wasted.

Diagram 1 — Reads and writes take two different paths

READ

App → Cachechecked first → miss → Databaseonly reached on a miss

WRITE — THE ORDER IS DECIDED BY THE PATTERN

The key idea to remember: all four patterns look the same on the read side (the cache stands in front of the database). They differ in when the database is written and in who loads data into the cache.

Section 2 — TTL and stale data

Link back to Session 7 — Section 1: what a cache is. That section's main content: a cache is a fast storage layer sitting in front of the database, holding a copy of the data so later reads do not have to go down to the database. Because the data in the cache is only a copy, it can be older than the original in the database — that is exactly the root of the stale data in this section.

TTL (time-to-live)

TTL is the lifespan of an entry in the cache. When the TTL runs out, the entry counts as a miss: the next read must go down to the database, fetch the newest data, and fill the cache again with a new TTL.

Stale data

Stale data is when the cache returns data that is older than the real data in the database. The cause: the database was updated, but the copy in the cache was not — the cache still holds the old copy and keeps serving it to readers.

How to choose a TTL

  • Highly dynamic data (data that changes fast) → set a short TTL: accept more trips to the database so the data never stays old for long.
  • Rarely changing data → a long TTL is fine: the copy in the cache almost always matches the database, so it rarely needs reloading.

Example 2.1 — Short TTL for fast-changing data

A product price on a shopping page changes many times a day. With a long TTL, customers would keep seeing a stale price long after the real price changed. So this kind of data gets a short TTL — a few seconds to a few minutes — so the cached price is refreshed from the database quickly.

Example 2.2 — Long TTL for rarely changing data

The country list in a sign-up form almost never changes. A long TTL — hours, even days — is safe for this kind of data, because the copy in the cache almost always matches the database.

Diagram 2 — The lifecycle of an entry under TTL

① FreshThe entry was just loaded from the database. Reads hit the cache; the data is new.
② Within TTLThe database may have changed → the cached copy is at risk of becoming stale data.
③ ExpiredThe entry counts as a miss. The next read goes down to the database for the newest copy.

The key idea to remember: TTL is the simplest way to limit how old cached data can get — the faster the data changes, the shorter the TTL must be.

Section 3 — Eviction policies

Link back to Session 7 — Section 2: where a cache sits (cache placement). That section's main content: a cache lives in memory (RAM) — fast, but with a much smaller and more expensive capacity than disk. Because memory is limited, the cache fills up sooner or later — and that is why the system needs the eviction policies in this section.

The problem: what happens when the cache is full?

When the cache is full, adding a new entry requires evicting (removing) an old one to make room. The question is: which entry gets evicted? An eviction policy is the rule that answers that question.

The 6 eviction policies

  • FIFO (first in first out): evict the entry that was inserted into the cache earliest.
  • LIFO (last in first out): evict the entry that was inserted into the cache most recently.
  • LRU (least recently used): evict the entry that has been unused for the longest time.
  • MRU (most recently used): evict the entry that was used most recently.
  • LFU (least frequently used): evict the entry with the lowest total access count.
  • Random: evict a random entry.

Example 3.1 — LRU evicts the entry nobody has touched for the longest time

The cache holds 3 entries: A, B, C. Recency of reads: A was read 1 minute ago, B was read 10 minutes ago, and C has not been read for 1 hour. The cache is full and a new entry D needs a slot. Under LRU, C is evicted — because C is the least recently used entry, it is the least likely of the three to be needed again soon.

Under MRU, on the other hand, A would be evicted, because A was used most recently — that fits workloads where data that was just used is unlikely to be used again right away, for example scanning through a long list exactly once.

Diagram 3 — One eviction under LRU

1 Cache is fullA · B · C — no free space → 2 New entry Dneeds a slot in the cache
3 C is evictedunused for the longest time — LRU → 4 New cacheA · B · D

The key idea to remember: a cache can never hold everything. Choosing an eviction policy means choosing which entry to sacrifice — based on arrival order (FIFO / LIFO), most recent use (LRU / MRU), number of uses (LFU), or nothing at all (Random).

Section 4 — Disadvantages of caching

Link back to Session 7 — Section 2 and Lesson 5: Section 2 of Session 7 covered the global cache — one Redis shared by every application server — alongside the local cache inside each server. Lesson 5 covered the load balancer and the idea of never letting one component become the single point that kills the system. This section connects those two ideas: the global cache itself, without HA, becomes the single point of failure for the whole system.

  • Stale data: the cache can drift away from the database. This is the root disadvantage: a cache is a copy, and a copy can always disagree with the original (see Section 2 of this session).
  • Cold start: a new cache node starts empty. The first wave of requests all miss and hit the database at the same time → the database gets overloaded exactly when the system is at its weakest.
  • Memory and cost: a cache lives in RAM — the most expensive kind of memory. The more data you keep in the cache, the bigger the bill.
  • Added complexity: adding a cache means dealing with two hard problems: invalidation (removing or expiring old data in the cache) and consistency (making sure the cache and the database do not contradict each other).
  • A global cache can become a single point of failure: if every application server shares one Redis (a global cache) and that Redis has no HA (high availability — a standby copy that automatically takes over when the main one dies), then Redis dying means every server loses its cache at the same moment, and all requests flood the database. Such a component is called a single point of failure.

Example 4.1 — A cold start overloads the database

A new cache node is added to the system at peak hour. The node is empty, so every request routed to it misses and goes on to the database. The database normally handles only the few requests that miss; now it suddenly has to handle almost all of them — and it can go down from overload, even though the database itself has no bug.

Example 4.2 — One shared Redis dies, the whole system loses its cache

Three application servers share one Redis as a global cache, and that Redis has no standby (no HA). When Redis dies, all three servers lose their cache in the same moment. Every request misses and floods the database — the same overload scenario as Example 4.1, but across the whole system at once. This is a single point of failure: one component dying takes the whole system down with it. The Load Balancer lesson (Lesson 5) taught the principle of avoiding a single point of failure at the server layer; the same principle applies exactly the same way at the cache layer.

Diagram 4 — A global cache without HA = a single point of failure

App server 1 App server 2 App server 3
↓ ↓ ↓  all of them share  ↓ ↓ ↓
1 shared Redis (global cache)NO HA → single point of failure
↓  Redis dies → every request misses  ↓

The key idea to remember: a cache makes the system faster, but the price is stale data, cold starts, memory cost, and extra complexity — and if a shared cache has no HA, the cache itself becomes the single point of failure.

Section 1 — Pattern comparison

  • Pattern comparison — comparing the cache access patterns side by side
  • Cache access pattern — the strategy an application uses to read and write through the cache
  • Read flow / write flow — the path a read / a write takes through cache and database
  • Pros / cons — advantages / disadvantages
  • Cache-aside = lazy loading — the application loads data into the cache only on a miss
  • Hit / miss — the requested data found / not found in the cache
  • Populate the cache — to fill the cache with data
  • Invalidate — to remove or mark an entry in the cache as no longer valid
  • Write-through — every write goes to the cache and the database together
  • Synchronously — at the same time, blocking until done
  • Fresh — (data) up to date, matching the database
  • Write-behind = write-back — write to the cache now, to the database later
  • Asynchronously — later, in the background, without blocking
  • Crash — a sudden failure of a system or process
  • Data loss — permanently losing data
  • Implementation — the work of building something
  • Refresh-ahead — refreshing entries just before they expire
  • Expire — to reach the end of a lifespan and stop being valid
  • Latency — the delay before a response arrives
  • Prediction — a guess about what will be needed in the future

Section 2 — TTL and stale data

  • TTL = time-to-live — the lifespan of a cache entry
  • Stale data — cached data that is older than the real data in the database
  • Copy — a duplicate of the original data
  • Highly dynamic data — data that changes very often
  • Rarely changing data — data that almost never changes
  • Short TTL / long TTL — a brief / an extended lifespan for an entry
  • Lifecycle — the stages an entry goes through from creation to expiry
  • Expired — past the end of its TTL, no longer valid

Section 3 — Eviction policies

  • Eviction policy — the rule that decides which entry leaves a full cache
  • Evict — to remove an entry from the cache
  • Full — (a cache) with no free space left
  • Capacity — how much a cache can hold
  • FIFO = first in first out — evict the earliest inserted entry
  • LIFO = last in first out — evict the most recently inserted entry
  • LRU = least recently used — evict the entry unused for the longest time
  • MRU = most recently used — evict the most recently used entry
  • LFU = least frequently used — evict the entry with the lowest access count
  • Random — evict an entry chosen at random
  • Scan — to walk through a long list from start to end

Section 4 — Disadvantages

  • Disadvantage — a downside or drawback
  • Cold start — a new cache node starting completely empty
  • Overloaded — given more work than it can handle
  • Memory — RAM, where a cache lives
  • Cost — the money a resource takes to run
  • Complexity — how hard a system is to build and maintain
  • Invalidation — removing or expiring old data in the cache
  • Consistency — the cache and the database agreeing with each other
  • Global cache — one cache shared by all servers
  • Local cache — a cache inside each individual server
  • HA = high availability — the system stays up even when a component dies
  • Standby — a backup copy waiting to take over
  • Single point of failure — one component whose failure takes the whole system down
  • Load balancer — the component that spreads traffic across servers (Lesson 5)
