1. What Is Cache?

Cache stores previously computed results, so the next request can reuse them instead of computing them again.

A cache in front of the database absorbs reads (takes the read traffic first). This reduces database load and latency (response delay).

Every read checks the cache first.

Hit

The cache has the data. Return it immediately.

Miss

The cache does not have the data. Fetch it from the database, store it in the cache, then return it.

2. Where to Put the Cache (Placement)

  • Client-side cache — stored on the client.
  • CDN cache — content cached close to the user.
  • Web server cache — for example Varnish and Nginx reverse proxy.
  • Database cache — query cache and buffer pool.
  • Application cache — in RAM, for example Memcached and Redis.
Example 1

Distributed Cache

Many cache nodes. Each node holds part of the data.

Total capacity = the sum of all nodes. One node down loses only its part.

Example 2

Global Cache

One shared cache for all servers — for example, sessions in Redis.

Any server can handle the next request. No sticky server needed.

3. What to Cache (Granularity)

Query-Level

Cache by the hash of the query.

Weak point: invalidation (removing stale entries) is complex and cascading — one change can affect many cached queries.

Object-Level

Cache whole objects, for example:

  • User sessions
  • Rendered pages
  • Activity streams
  • The user graph

4. Four Cache Patterns

Pattern 1

Cache-Aside (Lazy Loading)

How: the app checks the cache first. On a miss, it reads the database and fills the cache.

Strengths: only requested data is cached. The system still works if the cache fails.

Weaknesses: 3 trips on a miss, stale data, and an empty cache after a failure.

Pattern 2

Write-Through

How: write to the cache and the database synchronously (at the same time).

Strength: no stale data after a write.

Weaknesses: high write latency, most written data is never read, and a new node stays empty until it is updated.

Pattern 3

Write-Behind (Write-Back)

How: write to the cache first. Write to the database asynchronously (later, in the background).

Strengths: low write latency. Good for write-heavy data.

Weaknesses: data loss if the cache crashes, and higher complexity.

Pattern 4

Refresh-Ahead

How: the cache refreshes data automatically before it expires.

Strength: very low read latency.

Weakness: bad predictions are worse than no prediction.

Quiz — 10 Questions and Answers

Session 7 only — Sections 1–4.

Question 1

You added a cache. Cache-aside or read-through, and why?

Answer

Cache-aside by default: the app owns the miss logic and still reads the database if the cache fails. Use read-through only when you want the load logic centralised.

Source: online interview question.

Question 2

On a write, how do you keep the cache and the database consistent?

Answer

Invalidate the key on write — delete it so the next read reloads it — or use write-through to update both synchronously.

Source: online interview question.

Question 3

Write-through, write-back, or write-around here?

Answer

Write-through for data read soon after a write, when consistency is worth the latency. Write-back for speed when losing recent writes is acceptable. Write-around for write-once, rarely-read data.

Source: online interview question.

Question 4

How would you design a cache strategy like cache-aside, write-through, or write-behind?

Answer

Cache-aside reads the cache first, reads the database on a miss. Write-through updates both on every write. Write-behind writes the cache now, writes the database later. Choose by freshness need and traffic type.

Source: online interview question.

Question 5

What is caching? What are the types of caching?

Answer

Caching stores frequently accessed data in fast storage to reduce latency and database load. Types: in-memory cache (Redis, Memcached), browser cache, CDN cache, and database query cache.

Source: online interview question.

Question 6

How would you implement caching in a high-traffic API?

Answer

Use cache-aside with Redis. The app checks the cache first, reads the database on a miss, and fills the cache.

Source: online interview question.

Question 7

The database is getting hammered. How do you fix it?

Answer

Add a Redis cache with cache-aside for reads. Cache the read-heavy data and reduce the database load.

Source: online interview question.

Question 8

What happens if Redis goes down? What happens if the cache fails?

Answer

With cache-aside, reads fall through to the database. It is slower, but there is no data loss and the system still works.

Source: online interview question.

Question 9

A user updated their profile but still sees old data. Why, and how do you fix it?

Answer

The cached profile is stale. Fix it by invalidating that user's cache entry on update, so the next read loads fresh data from the database.

Source: online interview question.

Question 10

Distributed cache vs Global cache?

Answer

Distributed: many nodes, each holds part, total capacity is the sum, one node down loses only its part. Global: one shared cache for all servers — for example, sessions in Redis — any server can serve the next request.
